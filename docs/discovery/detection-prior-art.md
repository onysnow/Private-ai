# Detection: prior art (research of 10 October 2026)

For `detection-design.md`. Each entry: what it is, its licence as found, and what the Workbench can take from it. Generated from the research output; read the links before relying on a detail.

## Transaction monitoring and AML engines

- **Tazama (Linux Foundation, formerly Mojaloop FRMS)** (Apache-2.0). https://github.com/tazama-lf/docs ; https://frmscoe.atlassian.net/wiki/spaces/FRMS/pages/6586489/Rule+Processor+Overview ; https://frmscoe.atlassian.net/wiki/spaces/FRMS/pages/84344839 ; https://frmscoe.atlassian.net/wiki/spaces/FRMS/pages/84344852 ; https://github.com/tazama-lf/rule-901
  - How: Pipeline: TMS API (validate message, store history, update network graph) -> Event Director (a 'network map' decides which rules and typologies run on each transaction) -> rule processors -> typology processor -> TADProc (collects all typology results, writes the evaluation to DB, can push JSON to case management). Each rule is one behaviour, coded as its own TypeScript processor (handleTransaction -> determineOutcome), while its calibration lives in a versioned JSON config (id like '006@1.0.0', cfg version). Config has: parameters (e.g. maxQueryLimit, maxQueryRange, tolerance); exitConditions (cases where the rule cannot be evaluated, e.g. insufficient history, each with subRuleRef '.x00'/'.00', outcome and a human 'reason'); and either bands (lowerLimit >=, upperLimit <, subRuleRef, reason, e.g. '.02 Two similar amounts detected in the most recent transactions from the debtor') or cases (explicit value matches with a '.00' else branch). The overview page says 'result bands may change as rules are calibrated' while exit conditions are static for the life of a rule. Typology config lists rule sub-results with a weight for true/false (e.g. 006 .02 true=200, .03 true=300, 078 .02 true=1), an expression combining them (operator '*' or presumably '+', over terms), and workflow alertThreshold (200) and interdictionThreshold (300). One rule output can feed many typologies. Explanation is the chain typology -> rule -> subRuleRef -> reason string written in config; the docs page I read did not show a richer explanation format.
  - For the Workbench: Copy the rule format, not the code. Tazama is a Node/TypeScript streaming service built for payment messages, so it is not a Python library and its runtime does not fit a local-first FastAPI app. Its split is a strong fit for the 1,582-indicator catalogue: (1) one detector = one behaviour, reusable by many indicators; (2) calibration in versioned data (bands with reason strings) separate from code; (3) explicit 'cannot evaluate' exit conditions with their own reason, which maps directly to the Workbench's 'what the records cannot show'; (4) a typology layer that combines detector sub-results with weights into a composite, which maps to indicators built from several warning signs. Bands map naturally onto Faint/Strong/Textbook. Drop interdiction (no blocking in journalism).
- **Marble (checkmarble)** (Elastic License 2.0 (read from LICENSE in both checkmarble/marble and checkmarble/marble-backend); not OSI open source. Snoozes are not in the free plan.). https://github.com/checkmarble/marble ; https://docs.checkmarble.com/docs/rule ; https://docs.checkmarble.com/docs/decision-1 ; https://docs.checkmarble.com/docs/versioning ; https://docs.checkmarble.com/docs/trigger ; https://docs.checkmarble.com/docs/aggregations.md ; https://docs.checkmarble.com/docs/rule-snoozes.md ; https://docs.checkmarble.com/reference/getdecision.md
  - How: Scenario = trigger object + trigger formula (a boolean gate deciding which records are evaluated, also scoping batch runs) + rules. Each rule has name, description, rule group (tag), a score modifier (added to the global score if the rule is true; may be negative) and a formula built from operands (value, variable, or nested result) and operators, edited in a no-code builder. Aggregation variables (count, count distinct, sum, avg, min, max) over a related table with filters; look-back windows are expressed as filters (e.g. amount > 10x the user's 2-month average). Functions include string similarity, datetime functions, 'multiple of a threshold', and lists. Global score maps to an outcome through three thresholds: approve / review / block_and_review / decline. Lifecycle: one editable draft per scenario, committed into read-only versions; one version live at a time; activation replaces the live version. Decision record stores score, outcome, scenario id + iteration + version, and per-rule rows: rule_id (stable across versions), name, outcome (hit / no_hit / snoozed / error), score_modifier, and error. Rule snoozes: after human review in a case, a rule can be silenced for one end user for up to 180 days, with comment and audit history; snoozes are tied to rule version lineage.
  - For the Workbench: Learn from and copy patterns only. Go service plus Elastic License 2.0 rules out embedding it. Patterns worth taking: (a) a trigger/applicability gate before evaluation, i.e. 'does this case have the FtM schemas this indicator needs'; (b) draft -> immutable version -> one active version for every detector, with each flag recording detector id + version; (c) a per-detector result row with hit / no_hit / suppressed / error, so 'did not run' and 'errored' are never confused with 'clean'; (d) human-reviewed, time-limited, per-entity suppression with a comment, which matches a journalist dismissing a flag with a reason; (e) aggregation-as-data (function + field + filters + window). Do not copy the approve/decline outcome model: Workbench flags are leads, not decisions.
- **Jube** (AGPL-3.0-or-later). https://github.com/jube-home/jube ; https://jube-home.github.io/aml-fraud-transaction-monitoring/ ; .../Configuration/Models/AbstractionRules/ ; .../Configuration/Models/BasicActivationRules/ ; .../Configuration/Models/TTLCounters/ ; .../Configuration/Models/Backtest/
  - How: Staged model: gateway rules -> abstraction rules (aggregate statistics from cached history: search key such as IP or account, search interval and value as the look-back from the transaction's reference date, function type count/sum/average/median/distinct count/max/min/same count/since, function key field) -> abstraction calculations -> adaptations (ML) -> activation rules (the only stage that acts; boolean code fragments over Payload, TTL counters, Abstraction, Adaptation, Sanctions, etc.). Rules are written in a Builder (field/operator/value) or a Coder; the docs say rules are VB.NET fragments compiled by the engine. Activation rules have priority (chaining), maker-checker ('Approved By Review' required to activate), optional case creation, response elevation, sampling, suppression, visibility. TTL counters are keyed counters with an expiry interval, incremented by activation rules. Backtest: runs the rule as currently edited over archived transactions using the values the engine had at the time, read-only, reports a funnel, confusion matrix, precision/recall/F1/specificity, fired rate, and example transactions with the values the rule read.
  - For the Workbench: Learn from only. C#/.NET runtime and VB.NET rule code do not fit a Python app, and AGPL would impose obligations if code were copied. Take: (1) the separation of 'abstraction' (named, reusable measurements over a look-back window keyed by entity) from 'activation' (the rule that compares measurements to thresholds), which would let 1,582 indicators share a small set of computed measurements over the FtM graph; (2) maker-checker before a rule goes active; (3) the backtest design, especially recording the values each rule read so a hit or miss can be explained, and replaying against a labelled set (the Workbench's equivalent: seeded test cases with known warning signs).
- **Apache Fineract** (Apache-2.0 (Apache project; licence file not opened)). https://fineract.apache.org/
  - How: Not applicable for detection. Search results did not surface any official Fineract AML module.
  - For the Workbench: Not usable for detection. No evidence of an AML rule engine in Fineract.
- **Oracle FCCM / Behavior Detection / Transaction Monitor Cloud** (Commercial, proprietary). https://docs.oracle.com/en/industries/financial-services/ofs-analytical-applications/behavior-detection/8.1.2.9.0/bdatu/scenario-threshold-editor.html ; .../8.1.2.9.0/bdatu/scenario-tuning.html ; .../8.1.2.10.0/bdatu/using-graduated-value-scoring-editor-scenario.html ; .../8.1.2.9.0/bdatu/simple-scenario-scoring-rule-editor.html ; https://docs.oracle.com/en/industries/financial-services/ofs-analytical-applications/auto-scenario-calibration/25.01.01/ascuc/scenario-execution.html ; https://docs.oracle.com/en/cloud/saas/readiness/financial-services/2024/fccm-248/248-fccm-wn-f35254.htm
  - How: A scenario ships with a 'base threshold set' of sample values. Additional threshold sets let the same scenario run against different segments (example: USD 100,000 / EUR 150,000 / JPY 125,000; jurisdiction sets); fields can 'Inherit Base Value'. Unused thresholds are marked Inactive, and some thresholds are conditional on others (All Jurisdictions = N activates Included Jurisdiction Codes). Each threshold set has an ID the scheduler runs. Thresholds can only be set within a defined range or reset to sample. Scoring: Graduated Value rules map a match attribute's MinValue..MaxValue to MinScore..MaxScore; Simple Scenario Scoring rules add a fixed score; rule variations per threshold set keep a history of changes and comments. Scenario Tuning plots scenario 'binding values' (the computed quantities behind each alert) against analyst-assigned alert quality to find thresholds that would cut non-productive alerts. Auto Scenario Calibration generates 'tuning alerts' by lowering thresholds to see the population below the line, with one threshold set per jurisdiction per definition version. 2024 feature: initial threshold recommendations for new scenarios from a smaller sample (normally 6-12 months of history).
  - For the Workbench: Learn from only. Directly useful ideas: threshold sets as named, versioned parameter bundles per segment (for the Workbench: per jurisdiction, sector, or record type, e.g. state procurement limits differ); thresholds bounded to a valid range; inactive/conditional parameters; scoring as graduated value -> score (fits Faint/Strong/Textbook); keep the 'binding values' with every flag so the UI can show exactly which numbers tripped it and how far over the line they were; change history with a required comment on every threshold edit.
- **SAS Anti-Money Laundering (via Zencos paper presented at SAS Global Forum 2017)** (Commercial, proprietary). https://support.sas.com/resources/papers/proceedings17/0875-2017.pdf
  - How: Paper 875-2017 (Herhold, Overton, Hale): 'Each scenario is a set of rules aimed to generate an alert on probable suspicious activity'; each scenario has multiple parameters/thresholds needing tuning; look-back period is 'custom to the scenario' (example: calendar month). Segmentation top-down (business knowledge, e.g. commercial vs personal) then bottom-up (hierarchical clustering to pick k, then k-means; example 5 clusters), with tuning done per segment. Below-the-line testing samples alerts under the threshold (below the 60th percentile) and compares investigator dispositions to above-the-line alerts; investigators may receive BTL samples blind. The paper does not cover alert scoring or explanation.
  - For the Workbench: Learn from only. Segmentation and below-the-line testing are relevant once the Workbench has many cases with journalist dispositions (useful lead / dead end): it can then show how many dismissed flags sat just above a threshold and propose a recalibration. Peer-group comparison is mostly not applicable to a single investigation unless outside lookups supply a reference population (e.g. all contracts by the same agency).
- **NICE Actimize SAM (Suspicious Activity Monitoring)** (Commercial, proprietary). https://cn.niceactimize.com/Lists/Brochures/NICE_Actimize_AML_Suspicious_Activity_Monitoring_Brochure.pdf ; https://www.niceactimize.com/Documents/Anomaly_Detection_Datasheet.pdf
  - How: From marketing material only: out-of-the-box rules-based models combined with 'intelligent segmentation and profiling analytics'; new rules created in Actimize Policy Manager; 'smart peer grouping' and ML-driven automated threshold management/tuning. Anomaly datasheet: peer groups built automatically from account and party attributes and reassessed ongoing; recent activity compared to peers with ML such as isolation forests; anomalies become issues attached to new or existing alerts, risk-ranked; investigators see 'detailed explanations on each anomaly'; optional predictive score of SAR likelihood.
  - For the Workbench: Learn from only, and only at the concept level since technical docs are not public. Takeaway: several detections about the same entity are grouped into one alert rather than many, and each anomaly carries its own explanation; the Workbench should group flags by subject entity with per-indicator explanations under it.
- **FFIEC BSA/AML Examination Manual (suspicious activity monitoring section)** (US government publication). https://bsaaml.ffiec.gov/manual/AssessingComplianceWithBSARegulatoryRequirements/04
  - How: Monitoring sophistication 'should be dictated by the bank's risk profile'; 'Parameters and filters should be reasonable and tailored to the activity that the bank is trying to identify or control'; rule-based systems may use multiple, overlapping rules and complex filters; filters should be checked for gaps before implementation (example: a filter on daily cash above $10,000 misses structuring just below the CTR threshold); 'Management should document and be able to explain filtering criteria, thresholds used'; 'the monitoring system's programming methodology and effectiveness should be independently validated'; filters and thresholds periodically reviewed and tested; defined authority and approval for changes; clear escalation process from detection to disposition.
  - For the Workbench: Use as the design checklist for detector governance: each detector carries a written rationale for its thresholds, a known-gaps note (what just-below-threshold activity it misses, which is also an honest 'what the records cannot show'), a test set, a review date, and an approval record for changes.
- **Interagency Statement on Model Risk Management for BSA/AML (2021) and SR 11-7** (US government publication). https://www.federalreserve.gov/supervisionreg/srletters/SR2108.htm ; https://occ.gov/news-issuances/bulletins/2021/bulletin-2021-19.html ; https://www.federalreserve.gov/supervisionreg/srletters/sr1107.htm
  - How: 2021 statement (Fed SR 21-8 / OCC 2021-19, with FDIC, in consultation with FinCEN and NCUA): model risk principles 'may be appropriate considerations' but 'do not require any specific model risk management framework'; 'not all banks use models such as those described in the MRMG for BSA/AML compliance'; flexibility 'commensurate with the bank's risk profile' and to 'implement innovative approaches'. SR 11-7 validation elements: conceptual soundness ('assessing the quality of the model design and construction'), ongoing monitoring ('appropriately implemented and is being used and performing as intended'), outcomes analysis ('comparing model outputs to corresponding actual outcomes', incl. back-testing); effective challenge by objective informed parties; documenting limitations and assumptions; documentation detailed enough for someone unfamiliar to understand the model.
  - For the Workbench: Adopt the three validation elements as the detector test regime: conceptual soundness = each detector cites the catalogue indicator and source; ongoing monitoring = regression tests on fixture cases on every change plus run-time error/skip counts; outcomes analysis = track journalist dispositions per detector version. 'Limitations and assumptions' maps directly to the innocent-explanations and cannot-show fields.
- **FinCEN AML/CFT program rulemaking (2024 NPRM, superseded by April 2026 NPRM)** (US government rulemaking (summaries by law firms)). https://www.mayerbrown.com/en/insights/publications/2024/07/fincen-proposes-rule-reinforcing-financial-institutions-duty-to-design-and-maintain-risk-based-aml-cft-programs ; https://www.gtlaw.com/de/insights/2026/4/fincen-proposes-reforms-to-aml-cft-program-requirements
  - How: 2024 NPRM (June 28, 2024) required a documented, periodically updated risk assessment. Per Greenberg Traurig (April 2026), FinCEN published a new proposed rule on April 10, 2026 (comments to June 9, 2026) that supersedes and withdraws the 2024 proposal: resources toward higher-risk customers and activities, risk assessment updated promptly on significant change, an effective program 'need not prevent every minor instance', and institutions experimenting with ML/generative AI 'will not face additional supervisory or enforcement risk solely as a result of that experimentation'. Neither law-firm summary covered scenario design or model validation. Both are secondary sources; I did not open the Federal Register text.
  - For the Workbench: Context only. Supports prioritising detectors by risk/materiality rather than trying to fire on everything, and supports ranking leads instead of alert volume.
- **Wolfsberg Group Statement on Effective Monitoring for Suspicious Activity (2024)** (Wolfsberg Group publication (copy hosted by a third-party site)). https://www.moneylaunderingnews.com/wp-content/uploads/sites/12/2024/07/Wolfsberg-Group-MSA-Statement-for-publication.pdf
  - How: Urges 'a true risk-based approach' over 'prescriptive rules-based risk management routines'; criticises metrics on 'the quantity, as opposed to the usefulness' of reports; monitoring 'focused on material typologies and observed risks'; 'the best indicator of the quality and usefulness of SARs/STRs is direct feedback from government authorities'; ML models must be documented and analysed 'against the crystallised outcomes of detection'; warns 'No SAR/STR left behind' produces ineffective systems.
  - For the Workbench: Supports measuring detectors by usefulness (did the flag lead to a published or confirmed finding) rather than flag count, and capping or grouping low-value flags.

Lessons:

- Separate the detector's code from its calibration (Tazama, Oracle, Jube). A small library of Python 'measurement' functions over the FtM graph (count, sum, time gap, shared address, path length, ratio to a reference) plus per-indicator config written as data (YAML/JSON validated by pydantic) can cover far more of the 1,582 indicators than one hand-written rule per indicator. Today's 8 rules become the first measurements.
- Use Tazama-style bands with a reason string for each band, mapped to Faint/Strong/Textbook. Each band's reason is the plain-language sentence the UI shows. Lower limit inclusive, upper exclusive, as Tazama documents.
- Give every detector explicit exit conditions with their own reason ('needs Payment records with dates; none in this case'). This makes 'could not run' visible and feeds 'what the records cannot show'. Marble's per-rule hit / no_hit / snoozed / error status works the same way: record a result row for every detector on every run, not only for hits.
- Add an applicability gate before evaluation (Marble's trigger, Oracle's inactive or conditional thresholds). Indicators already list the FtM schemas they need and whether they need records, lookups or a person, so the gate can be generated from the catalogue. Indicators that need lookups or a person never auto-fire; they show as checklist prompts.
- Store the measured values with every flag (Oracle 'binding values', Jube backtest 'values the rule read'). The explanation panel can then say exactly which numbers tripped which band and by how much. This also drives ranking: distance past the threshold, band level, and how many independent indicators hit the same entity.
- Use a composite layer like Tazama typologies: an indicator or pattern made of several detector sub-results with weights and an expression. Unlike Tazama, keep the per-component breakdown visible instead of collapsing everything to one number, and use no block or decline thresholds.
- Version every detector config: draft, immutable version, one active (Marble). Each flag stores detector id, config version and catalogue indicator id, so a re-run after recalibration is traceable and old flags stay explainable.
- Use threshold sets per segment (Oracle): named parameter bundles by jurisdiction or sector, inheriting from a base set. Example: different procurement or reporting thresholds by state. Bound each parameter to a valid range, and require a comment on every threshold change, kept in a history (Oracle and FFIEC).
- Let a person suppress a flag with a required reason, scoped to one entity, with an expiry and an audit trail (Marble snoozes, 180-day maximum). In the Workbench, dismissing a lead should record why, and that disposition becomes the outcome data.
- Backtest and regression-test against fixture cases (Jube backtest, SR 11-7 outcomes analysis, SAS/Oracle below-the-line testing). Build seeded FtM test cases with known warning signs and known innocent look-alikes. Report a confusion matrix per detector version. Later, use journalist dispositions to show how many dismissed flags sat just above each threshold.
- Governance checklist from FFIEC and SR 11-7: written rationale for each threshold, known gaps (just-below-threshold evasion, e.g. structuring under $10,000), independent review (maker-checker as in Jube's 'Approved By Review'), periodic re-test, and documentation that someone unfamiliar can follow. These map onto fields the Workbench already shows: source, innocent explanations, and what the records cannot show.
- Group by subject (Actimize groups anomalies into an alert per entity). Show one lead card per entity or relationship, with the individual indicator hits under it, rather than a flat list of 1,000+ possible flags.
- Library choice: none of the open systems is embeddable in a Python app. Tazama is TypeScript microservices (Apache-2.0, pattern worth copying), Marble is Go under Elastic License 2.0, and Jube is C# with VB.NET rules under AGPL. Copy the formats and ideas, not code. A pure-Python design on networkx + pydantic needs no new package. If a safe expression language is wanted for config-written conditions, that would be a new dependency and needs an ADR. None was evaluated here.
- Avoid volume metrics and 'catch everything' targets (Wolfsberg 2024, FinCEN 2026 NPRM). Measure detectors by how often their flags become confirmed or useful leads, and prioritise high-materiality indicators first.

## Procurement and company-network engines

- **OCDS Cardinal (open-contracting/cardinal-rs; Python wrapper ocdscardinal)** (MIT (Open Contracting Partnership 2022)). https://cardinal.readthedocs.io/en/latest/ ; https://github.com/open-contracting/cardinal-rs ; https://cardinal.readthedocs.io/en/latest/cli/indicators/R/024.html
  - How: Rust core with a Python package, run from the command line: init, coverage, prepare, indicators. Settings live in an INI file with one section per indicator code (e.g. [R024] threshold = 0.05); leaving a section out turns that flag off, and a global [exclusions] section applies to all flags. Every flag has a documentation page laid out the same way: definition, methodology formula, the IQR fence (Q1 - 1.5*IQR or Q3 + 1.5*IQR, overridable by a fixed threshold), rationale, sources, a worked example ('In Atlantis...'), configuration, output, exclusions (the cases where the flag does not apply), assumptions, and a runnable demonstration. Output is JSON grouped by unit (OCID / Buyer / ProcuringEntity / Tenderer) then by indicator code, and every value is a decimal. A flag that did not fire is left out rather than written as zero. A 'Meta' block reports the quartiles and fences that were used, and '--map' links each flagged process to its flagged organisations. 'coverage' counts the non-empty JSON paths in the data. 'prepare' fixes data-quality issues and writes an issues CSV (line, ocid, path, value, 'not set/invalid/is zero'). The docs' 'review the results' step is still marked To do.
  - For the Workbench: Copy the format, not the library. The engine only reads OCDS procurement JSON, and the Workbench's FtM case graph is a different data model, so it cannot be dropped in. Its indicator-page structure maps almost one-to-one onto what the Workbench needs for each flag: definition, formula, rationale, sources, worked example, exclusions, assumptions, settings, demonstration fixture. Three ideas worth taking: (a) report the fence and statistics used alongside each result, which gives 'why it ranks where it does'; (b) a coverage pass that checks whether the fields a flag needs are populated before it runs; (c) an explicit exclusions list per flag. Any case that does hold OCDS data could run Cardinal as an optional external tool, which would need an ADR.
- **OCP 'Red Flags in Public Procurement' guide (2024, 73 indicators)** (Not stated on the page I opened). https://www.open-contracting.org/es/resources/red-flags-in-public-procurement-a-guide-to-using-data-to-detect-and-mitigate-risks/ ; https://www.open-contracting.org/wp-content/uploads/2024/12/OCP2024-RedFlagProcurement-1.pdf
  - How: Each indicator has a code, a stage, a type, a unit of analysis (buyer, bidder, process or market), a definition, a 'why is this a red flag' rationale, required OCDS fields, a methodology formula with a threshold, sources, and sometimes a real example. Three kinds of threshold: fixed legal ones (e.g. the minimum submission period), IQR statistical outliers (often computed per item category or procedure type), and proportion thresholds for buyer-level flags (example: more than 30% non-competitive, with an IQR fallback). Flags can be aggregated by counting them per unit, grouping related flags together (collusion), or building weighted indices; the guide warns that weights do not transfer between contexts and that the method must be transparent. Its false-positive advice: an indicator that fires for about 90% of procedures is too broad, and formulas should be fitted to local rules. It states that flags 'do not necessarily demonstrate the presence of corruption'.
  - For the Workbench: Usable as data and method, not code. Its per-indicator fields (stage, type, unit of analysis, rationale, required fields, threshold kind) are a direct template for extending the Workbench's 1,582-indicator catalogue schema. Two fields are worth adding: 'unit of analysis', and 'threshold kind' (fixed/legal, statistical outlier, proportion). Its guidance on grouping related flags rather than summing everything fits the Workbench rule that flags are leads with transparent ranking.
- **Government Transparency Institute / DIGIWHIST / Opentender Corruption Risk Indicators (Fazekas et al.)** (Not determined (QoG page lists source and citation; licence not stated in what I read)). https://datafinder.qog.gu.se/dataset/cri ; https://store.proebiz.com/02-aczibik_corr_measurement_ostrava__short_191106_16_9.pdf ; https://papers.ssrn.com/abstract=2711932 ; https://ug.opentender.eu/about/about-opentender
  - How: Indicators are computed per contract, then aggregated by simple or weighted average into a Corruption Risk Index. They are validated by correlating them with established corruption indices and with micro-level tests; the slides show advertisement period against the probability of single bidding (Portugal, TED 2009-2014). The QoG dataset gives coverage of about 4 million contracts in 32 European countries from 2011 to 2021, with a tax-haven list match for suppliers.
  - For the Workbench: Learn from it only. I found no open engine. The useful parts are (a) the validation idea: test whether a flag actually co-occurs with an outcome proxy before trusting its weight, and (b) the four indicator families, which match the Workbench's entity types (supplier risk maps to Company/Ownership/Address/Directorship in FtM; political connections map to Person/Membership/Family links). Supplier-risk items such as 'incorporated just before winning' and 'multiple companies at same address' can be checked from the case's own records with FtM dates and addresses.
- **OpenSanctions: nomenklatura (entity resolution / xref) and the logic-v2 matcher** (MIT). https://github.com/opensanctions/nomenklatura ; https://www.opensanctions.org/matcher/ ; https://www.opensanctions.org/docs/api/response/
  - How: The xref blocking index generates candidate pairs, which are scored by comparison. A Resolver stores judgements (same / not same / undecided) as a graph and infers links transitively (A=B and B=C gives A=C). The CLI runs xref -> dedupe (interactive judging UI) -> apply (writes merged output); the resolver database location is set by NOMENKLATURA_DB_URL. The matcher is rule-based with named, weighted features: in logic-v2, name_match 1.0, identifier/LEI/INN/IMO matches 0.85-0.98, address_prop_match 0.2, and negative features country_mismatch -0.2, dob_year_disjoint -0.15, dob_day_disjoint -0.25, gender_mismatch -0.2. The API returns, per result, an 'explanations' object keyed by feature, each with score, the query value, the candidate value, and a plain-text 'detail' (e.g. 'Birth years: 1965 vs 1951'). The default match threshold is 0.7. The docs state the score is 'not a risk score'.
  - For the Workbench: Usable as a library: it is MIT, Python and FtM-native, and sits in the same OpenSanctions ecosystem as the followthemoney and rigour packages the Workbench already uses. Adding it needs an ADR. Before any 'same person/company' indicator fires, nomenklatura can do the entity-resolution step and keep the journalist's judgements. The feature-explanation format (feature, weight, query value, candidate value, detail sentence) is the pattern to copy for every Workbench flag explanation. Negative features that lower a score map directly to 'innocent explanations'.

Lessons:

- Every mature engine separates the indicator definition (data and docs) from the evaluator. Cardinal's per-flag page (definition, formula, rationale, sources, worked example, exclusions, assumptions, settings, demonstration fixture) plus INI settings is the clearest model, and it fits the Workbench's catalogue entries almost one-to-one.
- Three kinds of threshold recur (OCP guide and Cardinal): fixed legal limits, statistical outliers (IQR fences, often per category), and proportions for unit-level flags. The catalogue should record which kind each indicator uses. For outlier flags, show the statistics used (Cardinal's Meta block); that is the honest answer to 'why it ranks where it does'.
- IQR outlier flags need a population. A single investigation usually has too few contracts to compute fences, so the Workbench should fall back to fixed or legal thresholds, or mark the indicator 'needs lookups' (an outside comparison population), rather than computing fences on n of about 5.
- Explanations work best as named, weighted features with the compared values side by side (OpenSanctions logic-v2: feature, score, query value, candidate value, a one-sentence detail). Negative features such as country_mismatch and dob_year_disjoint are a ready-made way to express 'innocent explanations' inside the scoring.
- Entity resolution comes before detection. Aleph xref and nomenklatura both block on normalised name fingerprints, then score, then keep human judgements (same / not same / undecided) with transitive inference. Without this step, 'same person' indicators (common director, shared owner) miss or double-fire. nomenklatura is MIT, Python and FtM-native, and is the natural fit, subject to an ADR.
- The type of link decides how far risk spreads: OpenSanctions carries sanction.control transitively through Ownership only, gives other links one hop (sanction.linked), and treats dated relationships with an end date as broken. Path indicators should record which edge types they traverse and respect dates.
- Write the limits down. OpenSanctions lists no ownership percentages, no nominees or trusts, and limited jurisdiction coverage; Open Ownership notes the queries were hard to answer. Each Workbench indicator's 'what the records cannot show' field should be authored in the same concrete way.
- Fixed-shape structural indicators can become data: a small FtM-labelled pattern graph matched with networkx DiGraphMatcher.subgraph_monomorphisms_iter (no new dependency), or Cypher text via grand-cypher (Apache-2.0, needs an ADR). Neither covers negation or absence, variable-length chains, or temporal and amount constraints well, so a hybrid is needed: declarative patterns for motifs, plus a small library of Python predicate and chain primitives (ownership depth, cycles with date ordering and amount retention as in Neo4j's ring demo, absence checks).
- Partial matches can provide levels: ISMAGS largest_common_subgraph, or counting how many pattern clauses are satisfied, could map to Faint, Strong or Textbook instead of a single yes/no.
- Reverse search ('screening' via percolation in OpenAleph, batch search in Datashare) turns every case entity's names into patterns run over each document's extracted text. The Workbench can do this locally with rigour normalisation, which makes document-mention indicators checkable from 'records' and re-runnable when new documents arrive.
- Validate before weighting. GTI checks indicators against an outcome proxy (single bidding) and established indices, and the OCP guide warns that weights do not transfer and that a flag firing on about 90% of cases is too broad. The Workbench should rank by transparent counts and groups of related flags (as OCP does for collusion) rather than an opaque composite score, and track how often each indicator fires as a tuning signal.
- Check coverage before running. Cardinal's 'coverage' counts non-empty fields, and 'prepare' writes an issues file. The Workbench can do the same per case, checking which FtM schemas and properties each indicator needs, before it reports a flag or reports 'not checkable with these records'.

## Rule formats

- **Sigma (rule format) + pySigma** (Spec: no licence on the spec page I opened; rules carry an SPDX 'license' field. pySigma: LGPL-2.1-only. sigma-cli: LGPL-2.1-or-later. RSigma: MIT (per mcpservers.org listing).). https://github.com/SigmaHQ/sigma-specification (spec v2.1.0, 2025-08-02); https://github.com/SigmaHQ/pySigma; https://sigmahq.io/docs/basics/modifiers.html; https://sigmahq-pysigma.readthedocs.io/en/latest/Rule_Validation.html
  - How: One YAML file per rule. Required fields are title, logsource and detection with a condition. Optional fields include id (UUIDv4), related (derived/obsolete/merged/renamed/similar), status (stable/test/experimental/deprecated/unsupported), description, references, author, date, modified, falsepositives, level, tags and license (SPDX). Detection is a set of named selections (field -> value lists, OR within a list) combined by a boolean condition: and/or/not, '1 of selection*', 'all of filter*'. Value modifiers are chained with '|': contains, startswith, endswith, all, re (with i/m/s flags), cidr, gt/gte/lt/lte, exists, fieldref (compare two fields), expand (pipeline placeholder), base64/base64offset, utf16 and windash. Correlation rules (separate multi-document YAML) have the types event_count, value_count, temporal, temporal_ordered, and, new in 2.1.0, value_sum, value_avg and value_percentile. Each has rules (by id or name, and can chain other correlations), group-by, timespan (for example 1h or 1d), condition (gt/gte/lt/lte/eq/neq plus a value, and a field for value_*) and optional aliases that map differently named fields across rules. Versioning works through id plus modified date plus related; the spec has no per-rule version number. Status shows maturity. pySigma (LGPL-2.1-only, v2.0.0 uploaded to PyPI 2026-10-04, Python >=3.11) parses rules and CONVERTS them into backend query languages through separate backend and pipeline packages. Its README does not say it evaluates rules against data itself. pySigma also ships rule validators (dangling detections or conditions, duplicate ids and titles, invalid modifier combinations, numbers written as strings). These are configured in YAML: 'all' with minus-prefixed exclusions, per-rule-UUID exclusions, and severity Low/Medium/High. Engines that evaluate Sigma directly exist outside Python: RSigma (Rust, MIT, includes a correlation engine and a linter) and Tenzir's sigma operator (it transpiles a rule into a filter expression).
  - For the Workbench: COPY THE RULE FORMAT; do not take the library. This is the closest match to the Workbench's needs. Its metadata already mirrors the indicator catalogue: falsepositives works like innocent explanations, level like Faint/Strong/Textbook, status like rule maturity, references like sources, and logsource like the 'data needed' FtM schemas. The selection/condition/modifier split and the correlation types (event_count, value_count, value_sum, temporal_ordered with group-by and timespan) cover thresholds, windows and sequences. Sigma has no graph paths. pySigma converts rules to queries rather than evaluating them over in-memory records, so the Workbench would need its own small evaluator (or a CEL backend) over FtM entities. The LGPL licence makes taking pySigma as a dependency possible, but an ADR would be needed and it gives little value without a backend. The validator design (YAML-configurable linters with per-rule exclusions) is worth copying for linting the 1,582-indicator catalogue.
- **Google CEL (Common Expression Language): cel-python (cloud-custodian) and cel-expr-python (C++ wrapper)** (Apache-2.0 (cel-python, cel-expr-python, common-expression-language)). https://raw.githubusercontent.com/google/cel-spec/master/doc/langdef.md; https://github.com/cloud-custodian/cel-python; https://github.com/cel-expr/cel-python
  - How: The spec states that CEL 'programs cannot loop forever' and that 'CEL functions have no observable side effects'. It is memory-safe and dynamically typed, with optional gradual type checking that rejects some programs before they run. It has macros (has, all, exists, exists_one, map, filter) that the host application opts into, and timestamp and duration types (duration units go up to hours, with no days or weeks). It has no in-language error handling and no mixed-type arithmetic. The spec includes a cost model: time and space are O(P*I) without macros or concatenation, nested macros can blow up exponentially, implementations may cap macro nesting, and custom functions must document their own cost. cel-python (Apache-2.0, v0.5.0 on PyPI 2026-01-31, Python >=3.10) is pure Python with a Lark-based parser. Its flow is Environment -> compile -> program(ast, functions) -> evaluate(activation). Its README lists deviations from the spec: no pre-checking of types, Python-style integer division, and errors raised as celpy.evaluation.EvalError. cel-expr-python (Apache-2.0, v0.1.3 on PyPI 2026-06-25) wraps the C++ implementation. It does compile-time type checking against declared variables, has serialisable compiled expressions, and supports custom functions in Python or C++ as well as late-bound functions. A third binding, common-expression-language (hardbyte, Apache-2.0, 0.10.0, 2026-09-15), also exists; I did not open its repo.
  - For the Workbench: USE AS A LIBRARY for the expression slot inside a Workbench rule file, with an ADR. CEL fits the 'no arbitrary code' requirement better than any other option here: guaranteed termination, no side effects, a documented cost model, and host-registered custom functions. The Workbench could register vetted graph helpers such as paths(), owners_of(), days_between() and same_address(), so that graph-path logic stays in reviewed Python and the per-indicator logic stays as data. CEL does not cover windows, sequences or aggregation across many records on its own. Those would come from list macros over pre-collected lists or from host functions. The choice between the pure-Python cel-python (no checker, known deviations from the spec) and the C++-backed cel-expr-python (type checker, early version 0.1.x) needs testing before deciding.
- **JSONLogic (json-logic-py, panzi-json-logic, python-jsonlogic)** (MIT for json-logic (nadirizr), json-logic-qubit, panzi-json-logic and python-jsonlogic). https://jsonlogic.com/; https://jsonlogic.com/operations.html; PyPI metadata for json-logic, panzi-json-logic, python-jsonlogic
  - How: Each rule is {operator: [args]}, nested into an AST. The site says 'We never eval()': rules can only read the data given to them and have no setters, loops or functions, and computation time is deterministic. Operations are var, missing, missing_some, if, ==, ===, !=, !==, !, !!, or, and, comparisons including 'between', max, min, arithmetic, map, reduce, filter, all, none, some, merge, in, cat, substr and log. - **DMN decision tables (OMG standard) via Drools; Python: pyDMNrules; related: GoRules ZEN** (DMN: OMG standard.   - How: Hit policies (per the Drools docs): Unique (overlap raises an error), Any (overlapping rows must agree), Priority (the output earliest in the output-values list wins), First (rule order) and Collect, with C+ sum, C< min, C> max and C# count. The expression language is FEEL, which has three-valued logic (true/false/null), dates, times, durations, ranges, lists and contexts. Conformance level 3 means full FEEL and all boxed expressions. Drools runs DMN 1.1–1.4 at level 3, on Java. pyDMNrules loads decision tables from Excel workbooks, uses pySFeel for FEEL, has decide(dict) and decidePandas(df) and a built-in test()/loadTest() runner, and includes a TCK-DMN folder. GoRules ZEN (Rust, MIT, Python package zen-engine 2.1.3 uploaded 2026-10-09) stores JSON Decision Model graphs made of decision tables, switches and expressions. Its tables are first-match, with collect columns available in 2.0.
  - For the Workbench: LEARN FROM IT. The hit-policy idea maps directly onto Faint/Strong/Textbook. A decision table per indicator could pick the strongest matching level (Priority) or count how many sub-signals fired (Collect C#). Unique and Any give a way to detect overlapping or contradictory level definitions when linting the catalogue. Taking pyDMNrules as a library would bring GPLv3 into the project, and Drools needs Java, so neither fits. - **Open Policy Agent / Rego (and Microsoft regorus)** (OPA licence not shown on pages I opened. opa-python-client: MIT. regorus: licence file not named on the page.). https://www.openpolicyagent.org/docs/policy-language; https://www.openpolicyagent.org/docs/policy-testing; https://www.openpolicyagent.org/docs/policy-reference/builtins/graph; https://openpolicyagent.org/docs/errors/rego-recursion-error/rule-name-is-recursive; https://github.com/microsoft/regorus
  - How: Datalog-style rules over the documents 'input' and 'data'. There are complete rules, partial set and object rules (for example 'violations contains x if {...}'), incremental definitions, functions, defaults, and array, set and object comprehensions. OPA runs as a Go binary or server (opa eval, opa run, an HTTP Data API). From Python, the options are opa-python-client (MIT, 3.0.0, 2026-09-30), which is a client to an OPA server, or regorus (a Rust interpreter, 'mostly compliant' with OPA v1.2.0, whose Python bindings are built with pyo3/maturin but 'we currently don't publish these bindings').
  - For the Workbench: LEARN FROM IT. Rego is the most expressive safe language here: it has joins, set comprehensions, counts and graph.reachable_paths, so indicators such as 'circular ownership' or 'payment to a company sharing an address with an official' are natural to write in it. But it needs a Go server or an unpublished Rust binding, which goes against a local-first Python app, and it would need an ADR plus a sidecar process. Three ideas are worth copying: (1) ban recursion and expose graph traversal only as vetted builtins; (2) tests are rules beside the rules, with coverage that shows which conditions never fired; (3) 'with' mocking, which works as fixture cases per indicator.
- **Elastic EQL (sequence rules) and ES|QL; Python: endgameinc eql** (eql Python package: AGPLv3. ES|QL/EQL in Elasticsearch: not checked.). https://www.elastic.co/guide/en/elasticsearch/reference/current/eql-syntax.html; https://github.com/endgameinc/eql; https://eql.readthedocs.io/en/latest/api/python_engine.html; https://www.elastic.co/docs/reference/query-languages/esql
  - How: Event queries take the form 'category where condition'. Sequence queries are '[step][step]' with 'by' join keys (shared field values), 'with maxspan' (all events within that duration of the first), 'until' (an expiry event), '!' for a missing event (needs maxspan), and 'with runs' (repeat a step 1–100 times). Sample queries group events by key without ordering. Pipes such as '| tail 10' come after the query, and there are string, math and conversion functions. The endgame eql Python package evaluates EQL locally. eql.PythonEngine provides add_query, add_custom_function, add_output_hook, stream_events and finalize (for aggregating pipes), and the CLI runs 'eql query -f events.json'. ES|QL is a piped language (FROM | WHERE | EVAL | STATS ... BY | LOOKUP JOIN | ENRICH ...) served through the Elasticsearch _query endpoint. The page I opened did not mention sequences or graph paths, and did not suggest it runs outside Elasticsearch.
  - For the Workbench: LEARN FROM IT. The EQL sequence grammar (by key, maxspan, until, missing step, runs) is the clearest model I found for timeline indicators, for example 'contract awarded, then a donation from the same company within 90 days, with no competing bid in between'. The Workbench could adopt the same concepts as fields in its rule format. The Python engine evaluates locally, but it is AGPLv3, which is a serious obligation for an app that may be distributed or hosted. ES|QL requires Elasticsearch, so it does not fit.

Throttling has a window duration and fields to group by, and happens before notable suppression. Adaptive response actions include Notable and Risk Analysis. The default RBA rules sum calculated_risk_score per risk_object and risk_object_type from the Risk data model: 'Risk Threshold Exceeded for Object Over 24 Hour Period' fires above 100 (an editable threshold, for example 200), and 'ATT&CK Tactic Threshold Exceeded ... Over Previous 7 days' fires on more than 3 tactics with at least 4 distinct sources. I could not open the risk-modifier and risk-factor scoring maths.
  - For the Workbench: LEARN FROM IT ONLY (proprietary, SPL needs Splunk). RBA is the most relevant design idea for the ranking side. Treat each indicator hit as a weighted contribution to an entity (Person or Company), not as an alert. Raise a lead only when several independent indicators or sources build up on the same entity, for example a count of distinct indicator families and distinct sources, like the 'more than 3 tactics, at least 4 sources' rule. This makes 'why it ranks where it does' explainable as a sum of listed contributions. Throttling by group-by fields suggests deduplicating repeated hits on the same entity pair.
- **YARA (yara-python)** (YARA: BSD-3-Clause (COPYING file); yara-python: Apache 2.0 (PyPI)). https://yara.readthedocs.io/en/stable/writingrules.html; https://raw.githubusercontent.com/VirusTotal/yara/master/COPYING
  - How: rule name { meta: (string/int/bool, not usable in conditions) strings: (text, hex with wildcards and jumps, regex, with modifiers nocase/wide/xor/base64/fullword) condition: (boolean over matches) }. Conditions support counts (#a), offsets (@a[i], 'at', 'in (range)'), sets (2 of ($foo*), any/all/none of them), for..of and for..in loops over ranges and module arrays, modules such as pe, external variables, and references to other rules. Documentation is for version 4.4.0. The rules relate matches within one scanned buffer; they cannot relate separate records.
  - For the Workbench: PARTLY AS A LIBRARY, NARROWLY. It is unsuitable for entity and link indicators because it cannot relate records. It could serve the subset of indicators that look for text patterns inside a document's extracted text (for example boilerplate phrases or template reuse across bids), but regex or the existing search may be enough for that. Its meta block plus 'N of (set)' conditions are a compact way to write 'at least 2 of these 5 textual signs' for Faint/Strong levels.
- **Great Expectations (GX Core)** (Apache-2.0). https://docs.greatexpectations.io/docs/reference/learn/terms/expectation/; https://docs.greatexpectations.io/docs/reference/learn/expectations/result_format/
  - How: An Expectation is 'a verifiable assertion about data', for example expect_column_values_to_not_be_null, with more than 50 built in. Domain keys (column, row_condition) say what data is checked, and success keys (value_set, mostly) say what counts as a pass. Expectations are grouped into Expectation Suites stored in an Expectation Store, and Checkpoints run suites against batches and trigger Actions. The result_format setting controls detail: BOOLEAN_ONLY, BASIC (unexpected_count, unexpected_percent, partial_unexpected_list of up to 20 items), SUMMARY (the default, adding counts and partial index lists) and COMPLETE (every unexpected value and index, plus unexpected_index_query, a query that fetches the failing rows). Custom Expectations subclass Expectation. Conditional Expectations (row_condition) are experimental.
  - For the Workbench: LEARN FROM IT. GX is tabular (Pandas, Spark, SQL), not graph-shaped, and it is a large dependency. Its result model is the part to copy: every check returns success, how many items failed, a capped sample of failing items, and a query that re-fetches the full set. The Workbench equivalent is a flag that carries matched entity ids, a capped preview, and a reproducible query or path for 'show me the records'. The 'mostly' success key (a pass if at least X% conform) is a good pattern for threshold indicators. GX could also check the case's own data before rules run, for example missing dates on Payment, so that flags state what the records cannot show.

Lessons:

- No single system covers everything the Workbench needs. Sigma gives the best rule-file metadata and correlation vocabulary, CEL gives the safest Python-embeddable expression engine, Rego gives the best model for graph traversal, EQL gives the best sequence grammar, DMN gives the level/hit-policy idea, Splunk RBA gives the ranking model, and Great Expectations gives the result/explanation shape. A home-grown YAML format that borrows from each, with CEL as the only expression language, is the design these findings point to.
- Sigma's rule metadata already matches the indicator catalogue almost field for field: falsepositives = innocent explanations, level = Faint/Strong/Textbook, references = sources, logsource = data needed (FtM schemas), status = maturity, id plus related (derived/obsolete/merged/renamed/similar) plus modified = versioning without a version number. Copying these names makes the format familiar and lets one indicator's levels and catch-alls point to related indicators.
- Safety pattern seen in both CEL and Rego: the language guarantees termination (CEL by construction and a cost model; Rego by rejecting recursion at compile time), and anything expensive or graph-shaped is a vetted host builtin (Rego graph.reachable and graph.reachable_paths; CEL custom functions with documented cost). For the Workbench, graph paths, ownership chains and address matches (rigour) belong in reviewed Python helpers registered with the expression engine, never in rule text.
- Sigma correlation types (event_count, value_count, value_sum, value_avg, value_percentile, temporal, temporal_ordered with group-by, timespan and aliases) together with EQL sequence features (by join key, maxspan, until expiry event, missing step '!', runs) give a ready vocabulary for timeline and threshold indicators over FtM Payment, Event and Ownership dates. The aliases idea solves joining on differently named FtM properties (for example payer vs owner).
- Ranking: Splunk risk-based alerting sums risk per object over a window and escalates only when the total, or the number of distinct tactics and sources, crosses a threshold. This gives an explainable 'why it ranks here' (a list of contributions) and stops single weak indicators from becoming leads.
- Testing: copy OPA's model (tests are data beside the rule, run by one command, with coverage showing conditions that never fired and mocking of inputs) and pyDMNrules's test() and loadTest(). Each indicator should ship positive and negative fixture cases as small FtM bundles, plus an innocent-explanation case that must not fire, or must fire only at Faint.
- Linting the 1,582-indicator catalogue: pySigma validators (dangling selections, duplicate ids and titles, invalid modifier combinations, YAML config with per-rule exclusions and Low/Medium/High severity) and the DMN Unique/Any hit policies (detect overlapping or contradictory level definitions) are worth copying as a catalogue linter.
- Licences rule out some engines as libraries: endgame eql is AGPLv3, pyDMNrules is GPLv3, and Splunk is proprietary. pySigma is LGPL-2.1, which is acceptable but only converts rules to queries and does not evaluate them. CEL bindings, yara-python, GX, zen-engine and rule-engine are permissive (Apache, MIT, BSD).
- Any new engine package (for example cel-python or cel-expr-python) needs an ADR. The candidates differ: cel-python is pure Python (Lark), has no type checker and has spec deviations listed in its own README; cel-expr-python wraps C++, type-checks at compile time and has serialisable compiled programs, but is at version 0.1.x. Both should be tested against a few real indicators before choosing.
- Result shape: copy Great Expectations' result_format. Each flag returns success, counts, a capped sample of matched records, and a reproducible query or path for the full set. That supports the requirement that each flag shows its source and what the records cannot show.

- **ILO Indicators of Forced Labour (2012 first edition; revised edition published 18 Nov 2025)** (ILO publication; the reuse terms were not shown on the pages I opened). https://www.ilo.org/publications/ilo-indicators-forced-labour ; https://www.ilo.org/publications/ilo-indicators-forced-labour-1 ; https://themekongclub.org/wp-content/uploads/2023/08/Forced-Labour-Indicators.pdf ; https://assuranceinaction.intertek.com/post/102ly7s/the-ilos-2025-forced-labour-indicator-update-what-stood-out-to-me
  - How: A booklet for front-line staff (labour inspectors, police, union and NGO workers). Each indicator has a short definition and real-life examples. The ILO pages call them clues to the 'possible existence' of forced labour that 'trigger further investigation', and say the list is 'not exhaustive'. The 2025 revision keeps the same 11 and rewrites the explanations: migrant status and recruiter behaviour under vulnerability, contract changes and language barriers under deception, deductions, falsified records and recruitment fees under wages and debt, penalties for refusing overtime, and employer-provided housing (according to an Intertek summary, 18 Dec 2025; the PDF itself was not opened). The Mekong Club checklist, built on the same 11, gives each indicator guiding questions and a 2 to 5 rating, and says threats should be judged from the worker's point of view (age, culture, economic status).
  - For the Workbench: Can be copied as checklist content. Each indicator can become a 'person' checklist item with guiding questions and an observed / not observed / unknown answer. The Mekong Club per-question rating and the 'judge from the worker's point of view' note fit the Faint/Strong/Textbook levels. The wording to copy is 'possible', 'trigger further investigation', 'not exhaustive'. There is no code or engine to reuse.
- **ILO 'Hard to see, harder to count' survey guidelines (2012)** (ILO publication; the reuse terms were not checked). https://respect.international/wp-content/uploads/2018/03/Hard-to-see-harder-to-count-Survey-guidelines-to-estimate-forced-labour-of-adults-and-children-ILO-2012.pdf
  - How: Each indicator is a yes/no variable rated strong or medium by expert consensus. Weak indicators were dropped or reclassified (p.22, fn 14). There are two sets of indicators: involuntariness and penalty. A dimension is positive when it has at least one involuntariness indicator and one penalty indicator, and at least one of them is strong (s.2.2, p.28). An adult counts as a victim if any dimension is positive. For children all indicators carry equal weight and no strong indicator is required (pp.30, 35). Worked example: deceived about wages (medium) plus wages withheld so the worker cannot leave (strong) counts as a victim.
  - For the Workbench: Its combination rule can be copied as data. Rules can be written as 'need ≥1 from group A AND ≥1 from group B AND ≥1 marked strong', and the combiner works on indicators that are already confirmed, so it is plain Python and needs no new package. This gives the Workbench an explicit, published rule for when several faint flags together become a stronger lead, instead of inventing its own weights. Two cautions: it is a survey-measurement rule, not a legal finding, and a flag built on it should still say so.
- **FATF–Egmont 'Trade-Based Money Laundering: Risk Indicators' (March 2021)** (FATF publication; terms not checked). https://www.cbr.ru/Content/Document/File/119937/TBLMRI.PDF
  - How: A prose list of indicators. It says 'The existence of a single indicator ... may not alone warrant suspicion', that one indicator may only justify closer monitoring, that 'the occurrence of several indicators could also warrant closer examination', that indicators must be read against 'the totality of the customer profile', and that the list is 'By no means ... a conclusive list'.
  - For the Workbench: Only to learn from, plus wording. It is an authoritative source for the Workbench rule that one flag is a lead, never a finding, and that several co-occurring flags raise priority. The innocent-explanations panel and the ranking text can cite it.
- **Berkeley Protocol on Digital Open Source Investigations (OHCHR / UC Berkeley HRC, 2022)** (UN publication). https://unipd-centrodirittiumani.it/public/docs/OHCHR_BerkeleyProtocol.pdf ; https://www.ohchr.org/sites/default/files/2024-01/OHCHR_BerkeleyProtocol.pdf
  - How: The table of contents gives the investigation cycle: online inquiry, preliminary assessment, collection, preservation, verification, investigative analysis, then reporting (ch. VII). Passages I could read: para 25, investigators 'should record any tools or software used' and 'Automated processes and software must be understood by users and be explainable in court'. Para 27, guard against personal, cultural and structural bias by 'developing and deploying multiple working hypotheses and not favouring any particular theory'. Para 30, 'Analytical conclusions should not be exaggerated or overstated' and acknowledge 'weaknesses in the underlying data'. Para 35, errors should be corrected, with a way to report them. Paras 55–59: assess each item for authenticity, reliability, relevance and probative value, and weigh it against corroborating or contradicting items. A video must be authenticated, and the statements in it verified separately.
  - For the Workbench: Learn from it and copy its rules into the flag design. 1) Each flag records the method that produced it: rule id and version, model name and version, prompt or hypothesis text, threshold. That is the 'explainable in court' requirement. 2) Each flag shows competing explanations, which the Workbench already does as 'innocent explanations'. 3) Separate 'the document says X' (quote verified) from 'X is true' (needs corroboration), following para 59. 4) Keep an error-correction trail. I could not read chapters VI and VII (verification steps, hashing, reporting confidence).
- **Minnesota Protocol on the Investigation of Potentially Unlawful Death (2016)** (UN publication). https://www.icla.up.ac.za/images/books/MinnesotaProtocol.pdf
  - How: It says it is not 'a step-by-step handbook' (para 3) and gives guidelines plus forms. Para 49: all material 'should be secured, recorded and logged' with source, date and time. Para 54: information management should give 'an audit trail that can demonstrate that evidence has not been tampered with'. Para 65: chain of custody, each item 'uniquely referenced and marked'. Para 31: impartiality, pursue exculpatory as well as inculpatory evidence. Para 48: pursue all legitimate lines of inquiry. Para 53: review strategy periodically and when new material arrives. Para 24: triangulate. Para 25: a decision not to do an autopsy 'should be justified in writing'.
  - For the Workbench: Learn from it and copy its patterns. 1) Checklist items a person must confirm should record who, when, the source and how it was established. 2) Every 'not done / not applicable' choice on a checklist needs a written reason, as with para 25. 3) Exculpatory evidence is a first-class field on a flag, not an afterthought. 4) Re-run detection when new material arrives (para 53). Its forms (case details form) show that a checklist can be a structured record. It has no indicator engine.
- **Hugging Face Transformers zero-shot-classification pipeline (NLI-based)** (Apache-2.0 (transformers)). https://huggingface.co/docs/transformers/main/en/main_classes/pipelines
  - How: Classification is posed as NLI. The text is the premise, and each label is put into a hypothesis_template (e.g. 'This text is about {}.'). The entailment score becomes the label score. With multi_label=False the labels compete through a softmax; with multi_label=True each label is scored on its own. The output is a dict of the sequence, its labels and their scores. Caveat: the docs section was cut off in my fetch, so this description is partly the fetch model's general knowledge and not confirmed text.
  - For the Workbench: Could be used as a library, but that needs an ADR because transformers and torch are new and heavy dependencies. Each indicator definition could be turned into a hypothesis ('The passage describes workers whose identity documents are kept by the employer.') and run with multi_label=True over retrieved passages. The weakness is a 512-token limit for most models, so run it over passages, never whole documents.
- **MoritzLaurer deberta-v3-large-zeroshot-v2.0 (and the v2.0 family)** (MIT (weights); training-data licences vary, so prefer '-c'). https://huggingface.co/MoritzLaurer/deberta-v3-large-zeroshot-v2.0
  - How: About 0.4B parameters, MIT licence. Models without '-c' were trained on NLI data that includes non-commercial licences (ANLI, WANLI, LingNLI…). The '-c' variants use synthetic Mixtral data plus MNLI and FEVER-NLI, and the card recommends them when licence terms are strict. The card advises testing different templates and label wordings like prompt engineering, and using more descriptive labels. Most models in the family take 512 tokens; the bge-m3 variants take 8192 and are multilingual. The card says the model 'can only do text classification tasks' and inherits biases from its training data.
  - For the Workbench: Usable as a local model file for passage-level indicator screening once an ADR approves transformers/torch. Prefer a '-c' variant if the app may ever be used commercially. Treat its score as a ranking signal for 'which passages a person should read', not as a detection.
- **sentence-transformers (bi-encoders, cross-encoders incl. NLI and MS MARCO rerankers, sparse encoders)** (Apache-2.0). https://github.com/UKPLab/sentence-transformers ; https://huggingface.co/cross-encoder/nli-deberta-v3-base ; https://sbert.net/docs/cross_encoder/pretrained_models.html
  - How: Bi-encoders embed texts separately, so they can be indexed and compared by cosine similarity. Cross-encoders read a pair together and output a score, with no embedding. Their raw scores run roughly -10 to 10, or 0 to 1 with a sigmoid. Cross-encoders are too costly to run over all pairs, so the usual pattern is to retrieve with a bi-encoder or lexical search and then rerank with a cross-encoder. The sbert pages I fetched list 'Retrieve & Re-Rank' but their bodies were cut off. cross-encoder/nli-deberta-v3-base is trained on SNLI and MultiNLI, outputs [contradiction, entailment, neutral] in that order, reports SNLI test 92.38% and MNLI mismatched 90.04%, and is Apache-2.0.
  - For the Workbench: Usable as a library after an ADR (it pulls in torch). Two uses: 1) embed indicator definitions and document passages for similarity-based candidate retrieval; 2) use an NLI cross-encoder to score passage→indicator-hypothesis entailment, and keep the contradiction score too. A contradicting passage is useful as an innocent-explanation candidate.
- **rank_bm25** (Apache-2.0). https://github.com/dorianbrown/rank_bm25
  - How: Implements BM25Okapi, BM25L and BM25+. BM25Okapi(tokenized_corpus), then get_scores(query) and get_top_n(query, corpus, n). It does no tokenising or normalising, which the caller must do the same way for corpus and query.
  - For the Workbench: Usable as a small pure-Python library, but it still needs an ADR. It may not be needed: SQLite FTS5 has bm25(), snippet() and highlight() built in (see that entry), so the database the Workbench already uses could do lexical passage retrieval without a new package.
- **SQLite FTS5 (bm25, snippet, highlight, porter and trigram tokenizers)** (Public domain). https://www.sqlite.org/fts5.html
  - How: bm25(table, weights...) gives lower values for better matches, with k1=1.2 and b=0.75 hard-coded. highlight(table, col, open, close) marks the matched phrases. snippet() returns a fragment of up to 64 tokens chosen to cover the most query terms. The porter tokenizer stems English. The trigram tokenizer matches any substring of 3 or more characters. Python's sqlite3 has FTS5 only if the linked SQLite was compiled with it; check with CREATE VIRTUAL TABLE ... USING fts5.
  - For the Workbench: Usable now with no new package. Each indicator gets a list of curated query terms and phrases, an FTS5 index over document chunks returns candidate passages, and snippet() and highlight() give the exact text to show. Postgres has an equivalent (tsvector, ts_rank, ts_headline), but I did not open its docs.
- **Reciprocal Rank Fusion (Cormack, Clarke, Büttcher, SIGIR 2009)** (Paper (algorithm is a few lines)). https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf
  - How: RRFscore(d) = Σ_r 1/(k + r(d)) with k = 60, fixed in a pilot study. It 'consistently yields better results than any individual system' and beat Condorcet Fuse.
  - For the Workbench: Copy the formula; it needs no library. It merges BM25 (FTS5) hits with embedding hits for each indicator before the NLI or LLM step. It works on ranks alone, so scores on different scales need no calibration.
- **SetFit (Hugging Face)** (Apache-2.0). https://github.com/huggingface/setfit
  - How: Fine-tunes a sentence-transformer contrastively and adds a classification head (scikit-learn or SetFitHead). It needs no prompts. The README reports that 8 labelled examples per class are competitive with a full RoBERTa-Large fine-tune on about 3k examples. The page I read did not mention multi-label support.
  - For the Workbench: A later step, after an ADR. Once journalists have confirmed or rejected passages for an indicator, those decisions are the training data, and a per-indicator SetFit model could replace zero-shot NLI for the indicators used most. This matches the AIMS.au finding that fine-tuned small models beat zero-shot prompting.
- **AIMS.au dataset and benchmark (ICLR 2025)** (CC BY 4.0 (dataset)). https://arxiv.org/html/2502.07022v1
  - How: 5,731 statements, more than 800k sentences, labelled by hired annotators (one annotator for 3 questions, two for 8), plus two expert gold sets of 50 statements. Vague or distracting sentences are labelled irrelevant. Results are scored by F1. Fine-tuned models far outperformed zero-shot: Llama3.2-3B scored macro-F1 0.156 zero-shot against 0.694 fine-tuned, GPT-4o zero-shot reached 0.439 without context, and BERT with context reached 0.718. Zero-shot models over-predicted relevance. Context (100 words either side) helped the fine-tuned models.
  - For the Workbench: Learn from it, and possibly use its data. It is direct evidence that 'classify each sentence against an indicator list' works best with small fine-tuned models, and that zero-shot LLMs over-flag. That supports retrieving, scoring and then sending to a person, never auto-confirming. Its 'vague statements count as irrelevant' rule is a useful labelling guide. The dataset could serve as an evaluation set for corporate-disclosure indicators.
- **LangExtract (Google)** (Apache-2.0). https://github.com/google/langextract ; https://raw.githubusercontent.com/google/langextract/main/langextract/resolver.py
  - How: The user gives a prompt and examples whose extraction_text is verbatim and in order of appearance; otherwise it warns about prompt alignment. The resolver aligns each extraction to the source. Exact alignment works on lowercased tokens with an order-preserving DP, so repeated mentions map to successive occurrences. The fuzzy fallback uses an LCS DP with coverage ≥ ceil(len×0.75) and density ≥ 1/3. The status is MATCH_EXACT, MATCH_LESSER, MATCH_FUZZY or None, and char_interval is None when it cannot find the text, so ungrounded output can be filtered out. It chunks long documents (max_char_buffer, max_workers) and can run several extraction_passes for recall. It writes JSONL plus a self-contained HTML viewer with highlights. It runs local models through Ollama (model_url=http://localhost:11434), but output_schema is not supported with Ollama.
  - For the Workbench: Either copy its alignment design or adopt it after an ADR. The key idea is to never trust a model's quote. Re-locate it in the stored document text, record the character span and an alignment status, and drop or downgrade anything that cannot be found. The Workbench's planned 'quote check' can copy this with no dependency, using exact token DP then LCS fuzzy with the same thresholds, and show MATCH_FUZZY as 'quote approximately found'.
- **Ollama structured outputs** (Ollama is MIT (not checked on this page)). https://ollama.com/blog/structured-outputs
  - How: Pass a JSON schema in the format parameter. In Python, pass a pydantic model's model_json_schema() and parse the reply with model_validate_json(). The post advises also telling the model to return JSON and setting temperature to 0.
  - For the Workbench: Fits the existing pydantic stack. The LLM step for an indicator returns {indicator_id, applies: yes/no/unclear, quote, reason, innocent_explanation}. The quote then goes through the LangExtract-style alignment check before a flag is created. This matches the pending 'Ollama adapter and quote check' task.

  - How: Checkpoints: roberta-large, deberta-v3-large, flan-t5-large (770M, best under 1B), and Bespoke-MiniCheck-7B (strongest; usable commercially per the page). Evaluated on LLM-AggreFact (11 datasets). It recommends splitting multi-sentence claims into sentences. It is on Ollama as 'bespoke-minicheck' (Sep 2024).   - How: Small NER models (gliner_small-v2.5, medium, bi-base, relex-large). It is 'optimized to run on CPUs and consumer hardware' and supports INT8, torch.compile and ONNX. The README example returns text and a label; it does not show character offsets, so I could not confirm them.
  - For the Workbench: An option after an ADR, for indicators whose data need is an FtM entity that has to be pulled from text first, e.g. a recruitment fee amount, a passport or identity document, a dormitory address. - **Marble (checkmarble) – open-core fraud/AML decision engine and case manager** (Open-source core plus a licensed enterprise tier (licence file not read); snoozes are not in the free plan). https://github.com/checkmarble/marble ; https://docs.checkmarble.com/docs/rule.md ; https://docs.checkmarble.com/docs/decision-1.md ; https://docs.checkmarble.com/docs/overview.md ; https://docs.checkmarble.com/docs/rule-snoozes.md ; https://docs.checkmarble.com/docs/ai-review.md
  - How: A rule has a name, description, rule group, score and formula. If true, its score (positive or negative) is added to a global score. - **OpenSanctions deduplication / nomenklatura** (nomenklatura code licence not checked; pairs dataset free for non-commercial use, businesses need a data licence). https://www.opensanctions.org/articles/2021-11-11-deduplication.md ; https://www.opensanctions.org/docs/pairs
  - How: Blocking on shared tokens (name parts, phone, tax numbers) with transliteration and n-grams, then term-frequency scoring to produce a ranked candidate list. Review happens in a text UI built with Textual that shows two entities side by side, and analysts sometimes check the web. A positive judgement creates a canonical ID; later judgements attach to it. Statements are kept unchanged and merges are applied at export, so merges can be undone. 34,600 decisions were made over about 8 weeks, and about 290k judgements from Aug 2023 were published as training pairs labelled positive or negative. Nomenklatura includes a basic statistical model trained on them.
  - For the Workbench: Copy the patterns, and possibly the library (FtM-native, but it needs an ADR). 1) A ranked candidate queue followed by a fast side-by-side human decision is the right review model for document-indicator candidates too: passage on the left, indicator definition and levels on the right, buttons for applies / does not apply / unsure. 2) Store judgements as reversible statements, not by overwriting. 3) Treat judgements as training data.
- **Aleph / OpenAleph cross-referencing** (Aleph MIT (not checked on these pages); OpenAleph licence not checked). https://docs.aleph.occrp.org/developers/explanation/cross-referencing ; https://openaleph.org/docs/user-guide/103/cross-reference/
  - How: Elasticsearch finds candidates. Names and identifiers are required, and names are normalised to fingerprints ('Siemens AG' becomes 'ag siemens'). An ML model then scores similarity using name (Levenshtein), country, identifier and address features and the count of shared properties; it was trained on journalists' manual judgements. Mentions extracted from files match one way only. The user clicks compute, then confirms or rejects each match. The docs say matches are 'suggestive, not definitive, always verify manually'.
  - For the Workbench: Learn from it, and integrate if OpenAleph is adopted for document reading, which the pending task #103 already plans. Mentions extracted from documents can feed 'records' indicators: names in documents matched to graph entities. Copy the 'suggestive, not definitive' wording and the confirm/reject step.
- **ICIJ Datashare** (Open source (licence not checked on this page)). https://www.icij.org/blog/2019/11/what-is-datashare-frequently-asked-questions-about-our-document-analysis-software/
  - How: Runs locally and can work offline: 'Strictly no data comes out of Datashare, even to ICIJ.' NER highlights entities that can be used as filters. Batch search uploads a list of queries and returns a spreadsheet of results for each. Users can star and tag documents.
  - For the Workbench: Learn from it. Batch search, meaning a list of terms per indicator run over all documents with a results table, is a proven, explainable journalist workflow. It is the simplest first tier of document-indicator detection and can be built on FTS5. It also confirms that fully local, nothing-leaves-the-machine is the expected standard for this kind of tool.
- **Trafficking-ad NLP research (Perez & Rivas 2023; dataset-challenges paper 2024)** (arXiv papers; dataset withheld). https://arxiv.org/abs/2311.13118 ; https://arxiv.org/html/2405.13348v1
  - How: Transformer classifiers with Integrated Gradients for interpretability, trained on pseudo-labels from heuristics (e.g. locations more than 300 miles apart, counts of unique identifiers) and from graph connections. The 2024 paper reports 90% textual duplication (5.05M ads, 516k unique) and no verified ground truth. Heuristics mislabel: one component was labelled positive because of multiple phone numbers, and shared identifiers link benign ads. Labelling bias was confirmed statistically (p = 0.004). It recommends deduplicating with documented thresholds, normalising identifiers, treating outputs as 'a supplementary tool within a holistic investigative framework', and involving advocates and experts with attention to harm to legitimate sex workers.
  - For the Workbench: Learn from it as a cautionary case. Indicator labels made from heuristics carry bias, so the Workbench must not train on its own unreviewed flags. Near-duplicate documents must be collapsed before counting 'how many documents show indicator X', or one copied text inflates the score. Innocent explanations must name the groups who could be harmed by a false flag.

Lessons:

- Every source agrees on one rule: an indicator is a clue, not proof. The ILO calls them clues to the 'possible existence' of forced labour that 'trigger further investigation'. FATF–Egmont says a single indicator 'may not alone warrant suspicion' and the list is 'By no means ... conclusive'. OpenAleph says matches are 'suggestive, not definitive, always verify manually'. Wording on flags should quote these sources.
- There is a published, explicit rule for combining indicators: ILO 2012 survey guidelines s.2.2. Indicators are tagged strong or medium and grouped into involuntariness and penalty. A dimension is positive only with at least one from each group and at least one strong (children: no strong needed). The Workbench can store this as data (group, strength, required-combination) and apply it after human confirmation, rather than inventing weights.
- Layered pipeline that the sources support for 'records-in-documents' indicators, cheapest first. (1) Lexical retrieval per indicator with curated terms, using SQLite FTS5 bm25/snippet/highlight with no new package, or rank_bm25. (2) Optional embedding retrieval (sentence-transformers) merged by Reciprocal Rank Fusion, k=60. (3) Passage scoring by an NLI zero-shot model with the indicator definition as the hypothesis, or a local LLM via Ollama structured output returning quote, reason and innocent explanation. (4) Quote grounding, copying LangExtract's resolver: exact token DP, then LCS fuzzy with coverage 0.75 and density 1/3, storing the char span and status and dropping anything unfound. (5) Optional reason-support check with MiniCheck via Ollama. (6) Human review queue. Nothing becomes more than a 'candidate' without step 6.
- Zero-shot classifiers and LLMs over-flag. AIMS.au: zero-shot Llama3.2-3B scored macro-F1 0.156 against 0.694 fine-tuned; GPT-4o zero-shot scored 0.439; zero-shot models 'over-predicted relevance'. So model scores should only order the review queue, never set Faint/Strong/Textbook on their own. Plan to collect reviewer decisions per indicator as training data. SetFit reports competitive results from about 8 examples per class.
- NLI models have a 512-token limit, except the bge-m3 variants at 8192, so detection must run over passages or chunks, never whole documents. Chunking already exists in the Workbench (extract_chunks), and passage IDs plus char offsets should be the unit every flag cites.
- Keep the contradiction score from NLI models (cross-encoder/nli-deberta-v3-base outputs contradiction, entailment and neutral). A passage that contradicts an indicator hypothesis is a ready-made innocent-explanation or exculpatory candidate. The Minnesota Protocol para 31 requires pursuing exculpatory as well as inculpatory evidence.
- Separate three statuses on a document-based flag, following Berkeley Protocol para 59, where statements in an item must be verified separately from the item itself: (a) quote found in the document (machine-checkable), (b) passage supports the indicator (model, then person), (c) the fact is true (needs corroboration). Today's flags risk merging these.
- Record the method on every flag: rule or model id and version, hypothesis or prompt text, threshold, retrieval terms, date. Berkeley Protocol para 25 says investigators 'should record any tools or software used' and 'Automated processes ... must be ... explainable in court'.
- For indicators that need a person (most of the ILO 11), build checklists, not detectors. Each item has a definition, guiding questions (as in the Mekong Club checklist), a strong/medium tag, an answer of observed / not observed / unknown / not applicable, who answered, when, the source (interview, inspection, document), and a written reason for 'not applicable', following Minnesota Protocol para 25. The Mekong Club checklist also says threats are judged from the worker's point of view.
- Review design to copy from AML and OSINT tools. Use a ranked queue with a side-by-side decision screen (OpenSanctions/nomenklatura Textual UI). Require an outcome to close a flag (Marble: False Positive / Valuable Alert / Risk Confirmed), adapted to 'innocent explanation holds' / 'useful lead' / 'confirmed'. Allow expiring per-entity snoozes with a justification and an audit event (Marble: max 180 days). Let notes on an entity carry over to its other flags. Keep a full event history. Store judgements as reversible statements (OpenSanctions).
- Do not copy auto-decisions (Marble's Decline/Block thresholds) or AI summaries that do not cite sources (Marble's AI Review does not describe citing sources, and its KYC enrichment sends data to the US). Both conflict with 'flags are leads' and local-first.
- Collapse near-duplicate documents before counting how many documents support an indicator. The trafficking-ad dataset had 90% duplication, and heuristic labels were measurably biased (p = 0.004). Never train on unreviewed flags.
- No new package is needed for tier 1: FTS5 for retrieval, pure Python for RRF and quote alignment, pydantic and Ollama over HTTP for the LLM, and MiniCheck via Ollama. transformers, torch, sentence-transformers, SetFit, GLiNER and LangExtract would each need an ADR. If adopted, prefer the MoritzLaurer '-c' zero-shot models for clean training-data licences.

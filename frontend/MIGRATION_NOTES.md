## Remaining hand-rolled markup (follow-up punch list)

- The `<section className="card">` panel-by-panel conversion is done -- every panel in `app/page.tsx` now renders through `Card`/`CardHeader`/`CardTitle`/`CardContent` (with `CardDescription` where the panel had an intro paragraph).
- Four `<select>`s are now migrated to `Select`/`SelectTrigger`/`SelectValue`/`SelectContent`/`SelectItem`: the connector-credentials provider picker (backup & restore panel, 2026-09-27), the source-type picker in the source & exact evidence capture panel (2026-09-27, static 6-option list), and the investigation-timeline panel's precision and status pickers (2026-09-27, static 5-option lists each: `day`/`month`/`year`/`range`/`unknown`; `asserted`/`verified`/`approximate`/`disputed`/`unresolved`). All four are plain literal `<option>` lists with no `.map()`. The provider picker's conversion was the first real usage of `components/ui/select.tsx` anywhere in the app, and it has a real cost worth knowing before converting more: first-load JS for `/` jumped from 173 kB to 207 kB (+34 kB), because `@radix-ui/react-select` (plus its focus/positioning machinery) was previously fully tree-shaken out and now isn't. This is a one-time cost, not a per-select cost -- confirmed by the three conversions since, none of which moved the bundle size at all (still 207 kB). All four selects were chosen specifically because they have zero test coverage (`grep`ed `tests/` for each state-variable name plus distinguishing placeholder/option text, and for the timeline pair also checked that the test file's use of matching literal strings like `'day'`/`'verified'` was mock API data, not a select interaction -- confirmed clean each time), so no interaction-test rewrite was needed for any of them. Most of the remaining `<select>`s ARE exercised via `user.selectOptions(...)` in `tests/` (known so far: `leadPriority`, `relSchema`, the relationship-evidence-attach select, `claimStatus`) -- converting any of those will also require rewriting that test's interaction to Radix's click-trigger-then-click-item pattern, on top of the `onChange`→`onValueChange` code change. Still-untested candidates as of this update: `extractionRelSource`, `extractionRelTarget`, `provider` (external-connectors panel), `inv`, `entityId`, `relSource`, `relTarget` -- re-verify test coverage before converting any of these too, since new tests could be added between cycles. No `Checkbox` component exists at all yet; adding one is a separate PR. No `Slider` component exists either, so the one `<input type="range">` in the app (claim confidence) also stays native.
- Most action controls still use native `<button>`, `<input>`, `<textarea>`, and `<select>`
- Dialog-like and menu-like interactions are still custom and can migrate to `Dialog` / `DropdownMenu`
- Claim/evidence and relationship workspaces still render custom list/row layouts that can migrate to `Table`, `Tabs`, and additional `Card` composition

## Follow-up strategy

1. Convert one workflow section per PR to keep risk and review size low.
2. Replace native controls in each section with matching shadcn primitives while preserving existing handlers/state.
3. Keep visual/structural-only scope (no behavior changes) and validate with `npm run typecheck` and `npm run build` each step.
